# Native Wayland upstream contribution checklist

Draft, inspected 2026-10-13 in the MemerGamer/uno fork, originally based on Uno 6.7.135 (`da217df231`). This records the checked-out repository's rules, including fork-local agent guidance; it does not establish current upstream policy or branch protection. Recheck upstream before submission. Nothing has been submitted or committed by this documentation task.

## Discuss and scope the contribution

- [ ] Search existing upstream enhancement issues before filing a new one; discuss this substantial feature with the team before proposing implementation for merge. Explain the scenario, missing behavior and design tradeoffs. Sources: [CONTRIBUTING.md](../../CONTRIBUTING.md), sections “Request a feature” and “Identifying the scale”; [issue triage](../articles/contributing/guidelines/issue-triage.md).
- [ ] File using the [enhancement form](../../.github/ISSUE_TEMPLATE/enhancement.yml), filling the required description and the use case, renderer, platforms and additional information. The current form has no Wayland platform option: explain Linux desktop/Wayland in the text rather than claiming it has a dedicated choice. Draft: [upstream issue/discussion](upstream-issue.md).
- [ ] Associate every implementation PR with an issue and put `**GitHub Issue:** closes #NUMBER` first. Documentation-only changes are exempt. Use a public upstream issue; the LinuxFiles issue motivates the feature but is not a substitute for the upstream tracking issue. Sources: [actual PR template](../../.github/pull_request_template.md), [AGENTS.md](../../AGENTS.md), “Pull Requests & Issues”.
- [ ] Target upstream `master` and replay/rebase the isolated Wayland work onto a recent upstream commit. The fork's 6.7 base and local release-feed maintenance are separate concerns, not permission to target a release branch upstream. Source: [PR guidelines](../articles/contributing/guidelines/pull-requests.md).
- [ ] Keep unrelated fork additions out; propose shared-service refactoring separately where useful and agree on it with maintainers. Source: [code style](../articles/contributing/guidelines/code-style.md), “Refactoring”.
- [ ] Keep public documentation self-contained and free of private tracker identifiers/URLs. Source: [AGENTS.md](../../AGENTS.md), “Public Documentation and Spec References”.

## Commits, API and code quality

- [ ] Use Conventional Commits for every commit and the PR title. Sources: [CONTRIBUTING.md](../../CONTRIBUTING.md), [Conventional Commits](../articles/uno-development/git-conventional-commits.md), [REVIEW.md](../../REVIEW.md). Use `feat(wayland): ...`, `fix(...)`, `docs`, `test`, `perf` or `chore` as appropriate; `reg` denotes an unreleased regression. The contribution guide's older summary/`Addresses #...` example does not supersede its mandatory Conventional Commits rule or the template's closing-issue line.
- [ ] Keep meaningful focused commits, squash fixups before submission and rebase to a recent default-branch commit. The [PR guide](../articles/contributing/guidelines/pull-requests.md) asks for the least possible meaningful commits; local [AGENTS.md](../../AGENTS.md) permits logical incremental commits for larger work and requests imperative descriptions under 50 characters. Do not commit these drafts: the author explicitly requested uncommitted files.
- [ ] Follow tabs, Allman braces, EditorConfig, nullable and header conventions; use `EventHandler`/`EventHandler<TEventArgs>`, never `event Action`. Use internal extension helpers and appropriate platform isolation. Sources: [.editorconfig](../../.editorconfig), [code style](../articles/contributing/guidelines/code-style.md), [AGENTS.md](../../AGENTS.md), [.claude/rules/code-style.md](../../.claude/rules/code-style.md), [platform targeting](../../.claude/rules/platform-targeting.md).
- [ ] Scope this to Linux Skia hosting and keep other targets compiling/behaving as before. Source: [AGENTS.md](../../AGENTS.md), “Development scope: Skia-first”.
- [ ] Audit additive public builder API, internal contracts and friend assemblies; do not expose framework internals merely to compile the new host. Review package/API diffs. Breaking changes require discussion, explicit Conventional Commit marking, impact and migration guidance; changes incompatible with WinUI are generally unacceptable. Source: [breaking changes](../articles/contributing/guidelines/breaking-changes.md); allow-list changes require agreement, not automatic suppression.
- [ ] Review new native/managed dependencies and public transitive pins case by case. Source: [dependency guidelines](../articles/contributing/guidelines/updating-dependencies.md). [Build artifacts](../articles/contributing/build-artifacts.md) says master merges publish prereleases: plan upstream packaging separately from fork-local CI/feed scripts.
- [ ] Before a later commit or PR, run the local eight-lens `/review-panel` and resolve findings. Source: [AGENTS.md](../../AGENTS.md), [.claude/commands/review-panel.md](../../.claude/commands/review-panel.md), [cheatsheet](../../.claude/review-panel-cheatsheet.md). This documentation task does not commit or open a PR and has not run the panel.

## Tests, samples and documentation

- [ ] Build the repository and pass relevant tests/CI. Sources: [CONTRIBUTING.md](../../CONTRIBUTING.md), [PR guidelines](../articles/contributing/guidelines/pull-requests.md), [creating tests](../articles/contributing/guidelines/creating-tests.md). Tests are expected for completed bugs/features; “too hard” exceptions are the team's decision, not the contributor's unilateral waiver.
- [ ] Use mocked unit tests for platform-independent logic, platform runtime tests for programmatically verifiable platform behavior, and UI tests for input/screenshots. Prefer runtime tests where possible and public API assertions for WinUI parity. The older guide calls mocked tests `Uno.UI.Tests`; local [AGENTS.md](../../AGENTS.md) names `Uno.UI.UnitTests`. Confirm the actual projects instead of copying historic paths.
- [ ] For behavior unsuitable for automation, add a manual SamplesApp sample and check neighboring samples. Source: [creating tests](../articles/contributing/guidelines/creating-tests.md), [SamplesApp guide](../articles/uno-development/working-with-the-samples-apps.md). Add `[Sample]`, themed resources and formatted XAML per [samples rule](../../.claude/rules/samples.md); sample files are glob-discovered.
- [ ] Apply local build validation: unit-test solution build, unit tests, `/runtime-tests` for UI changes, `/winui-runtime-tests` where parity is meaningful, and SamplesApp for visual changes. Sources: [AGENTS.md](../../AGENTS.md), [runtime test skill](../../.claude/skills/runtime-tests/SKILL.md), [WinUI runtime test skill](../../.claude/skills/winui-runtime-tests/SKILL.md). Native Wayland transport still needs real Linux compositor tests; WinUI cannot validate that transport.
- [ ] Use a matching solution/TFM override; never commit `crosstargeting_override.props`. Do not cancel builds; allow 15+ minutes. Fast local mode is not analyzer-strict CI validation. Sources: [AGENTS.md](../../AGENTS.md), [build-system rule](../../.claude/rules/build-system.md).
- [ ] Format SamplesApp XAML with XamlStyler; CI checks touched sample XAML. Sources: [code style](../articles/contributing/guidelines/code-style.md), [XAML workflow](../../.github/workflows/xaml-style-check.yml).
- [ ] Separate **Code review**, **Compile**, and **Runtime** evidence. Scratch projects/stubs do not establish integrated host correctness. For bug fixes reproduce first, name the broken invariant, fix its cause and show failing-before/passing-after tests. Sources: [AGENTS.md](../../AGENTS.md), [debugging discipline](../../.claude/rules/debugging-discipline.md).
- [ ] Add user documentation using [.feature-template-uno-only.md](../.feature-template-uno-only.md) because a Linux host has no WinUI equivalent; describe opt-in, native dependencies, fallback and limits. [.feature-template.md](../.feature-template.md) explicitly directs Uno-only features to that template. Validate docs with the [docs build workflow](../../.claude/skills/docs-build/SKILL.md) when integrating the published article.
- [ ] Fill every section and checkbox of the [PR template](../../.github/pull_request_template.md) honestly: tests/sample, docs, screenshot comparison results, no breaking changes, optional review of two other PRs. Leave unverified boxes unchecked. The test guide says snapshot comparisons were not gating at its writing; the PR template still asks contributors to validate their results.
- [ ] Obtain the two approvals described by the [PR guide](../articles/contributing/guidelines/pull-requests.md). [.mergify.yml](../../.mergify.yml) describes green `Uno.UI - CI`, two approving write/admin reviewers, no change requests, `ready-to-merge`, and no WIP/breaking-change block labels.
